01

How the stack got here

Three rounds of decisions, two of which reversed an earlier recommendation of mine. Recorded here because the reasoning matters more than the conclusion — if a constraint changes later, you’ll know which choice to revisit.
Web — replaced

Astro 7 → Next.js 16

Astro’s value is SEO, cold-visitor TTFB and shipping zero JS on content pages. Running local-only, all three are worth nothing. And its multi-page architecture loses client state on navigation — which for a persistent player, playback position and a mini-player is close to fatal. Every route here is behind login. That is Next.js territory.

Backend — replaced twice

Hono → FastAPI → Django 6 + django-ninja

Python because you asked to learn it. Django over FastAPI for one decisive reason: the admin is a free catalog CMS, which removes most of a vertical. The old objection — Django being sync — died with 6.0’s async ORM. django-ninja keeps Pydantic v2 and auto OpenAPI, so contract generation survives intact.

Deployment — deleted

Cloudflare → nothing

An entire section of this plan disappeared. No Pages, no R2, no Render, no adapter choice, and the Workers CPU limit that would have blocked a database-backed Python API is now irrelevant. Docker Compose is the whole infrastructure story.

Video — replaced

Mux → self-hosted HLS on disk

Every managed option costs money at rest. You transcode Blender’s open movies into a real multi-bitrate ladder with ffmpeg and serve them from local disk. You end up writing the signed-playback logic Mux would have hidden from you — which is the more instructive outcome anyway.

Considered and rejected — and why, in case you want to revisit
no

One universal Expo app (iOS + Android + web from a single codebase). Technically the strongest fit: it would halve the frontend work, drop you to 8 agents, delete packages/ui-spec, and make “same UI, colours change” structural rather than policed. Rejected because you chose learning breadth — two frontend paradigms teaches more than one. Revisit this the moment scope starts to hurt.

no

NestJS or Hono for an all-TypeScript stack. Would have collapsed the contract seam entirely — a shared Zod package, or tRPC with zero codegen — and Nest’s modules map neatly onto agent boundaries. Rejected because you already know JS, so it teaches you a framework’s opinions rather than a language. It is the most coherent stack and the lowest learning yield.

no

Django for admin plus FastAPI for the API. A real production pattern, but two Python apps and two ORM sessions is more moving parts than one person on one machine should carry.

On Graphify specifically

Strong fit, deliberately deferred to Phase 3

Why it fits: you are polyglot, and the chain Django model → OpenAPI → generated TS → two clients is exactly where grep fails and a real graph earns its place. Better still, if it resolves import and call edges it can detect when apps/web depends on something in apps/api that isn’t the generated contract — a boundary-violation detector, which is the enforcement layer from §05 done properly rather than by hand.

Why wait: a knowledge graph of an empty directory is nothing, so its value only starts once Phase 1 lands. And it is pre-v1, on an active v8 branch. You are already carrying NativeWind v5 preview; stacking two unstable dependencies on the critical path is how you end up debugging tools instead of the app. Adopt it as a read-only shared surface — it needs no path boundary, every agent can query it safely, and if it breaks nothing stops.

03

Three constraints worth knowing before you start

The earlier deployment constraints are gone with deployment. These three replace them, and all three are specific to running the whole thing on one Windows machine with a phone in your hand.
Constraint — local networking

Your phone cannot reach localhost

This is the one that wastes an afternoon. The Expo app running on a physical device is a different machine from the one serving Django and the HLS files. http://localhost:8000 resolves to the phone itself and fails silently in ways that look like CORS or auth bugs.

Design for it from day one: bind Django to 0.0.0.0, put your machine’s LAN IP in a single EXPO_PUBLIC_API_URL env var, add the same IP to Django’s ALLOWED_HOSTS and CORS origins, and open the ports in Windows Firewall — it blocks inbound LAN connections by default. The HLS base URL needs exactly the same treatment, or video will play on web and fail on device.

Constraint — auth architecture

React Server Components and a separate API server need a token handoff

Next.js RSC runs on the server, so it has no access to a token held in browser memory. With Django as a separate service, every server-side fetch has to carry credentials deliberately — forwarding the session cookie, or reading a httpOnly cookie in the server component and attaching a bearer header.

Decide this once, in the auth spec, and never again. Getting it wrong produces the classic symptom: pages render fine on client navigation and 401 on hard refresh. Mobile has no equivalent problem, because Expo is always a client.

Constraint — styling

NativeWind v5 is still on the preview track

Tailwind v4 syntax on native only exists in NativeWind v5, officially supported from Expo SDK 56 onward but not marked stable. The alternative pins native to v4 (Tailwind v3 syntax) while web runs v4 — two dialects of the same vocabulary, which quietly erodes the guarantee you asked for.

Recommendation: take the preview. The token package can emit both formats, so reversing this is a config change rather than a rewrite.

Project rule — private, not airgapped

The goal is no public exposure, not no network

The concern here is legal and privacy, not connectivity: don’t publish something that looks like Netflix, and don’t leak usage anywhere. That is not the same as an airgap — an airgap would break the TV, which is the whole point of the build. The app binds 0.0.0.0 and is reachable across your LAN and your tailnet. It is never reachable from the open internet.

On the legal question, briefly: what you are building is Jellyfin — a self-hosted media server streaming content you have rights to, to your own devices. That is a large, ordinary, legitimate category. The two rules that actually matter are never ship Netflix’s name, logo, wordmark or brand colour, and only stream content you have rights to (Blender’s open movies are CC-BY, so that is already handled). A UI of poster rows is a generic pattern shared by Disney+, Prime, Hulu, Plex and Jellyfin, and is not protectable. A private or public GitHub repo is equally fine.

How the boundary is enforced

Three layers, because prompts alone leak

1. Agent definition. Each .claude/agents/*.md frontmatter lists its tools, and its system prompt names its allowed paths. This catches the honest mistakes.

2. A pre-commit guard. scripts/check-boundaries.py reads an OWNERS.yml map and rejects a staged changeset touching paths outside the declared agent’s allowlist. This catches the rest.

3. CODEOWNERS plus a required check. The same map expressed as GitHub CODEOWNERS, so a cross-boundary PR is visible in review rather than merged quietly.

06

The spec-driven loop

Spec Kit is MIT-licensed and installs through uv, which you already have. It gives you a constitution, then a repeating cycle per feature. The command that matters most for your setup is /speckit.taskstoissues — it turns a task list into real GitHub issues, which is what connects specs to the board.

Per-feature command sequence

  1. /speckit.specify — requirements and user stories. No tech talk allowed here.
  2. /speckit.clarify — forces the underspecified bits into the open before they become guesses.
  3. /speckit.plan — the technical approach, bounded by the constitution.
  4. /speckit.tasks — the task list, each item tagged with its owning agent.
  5. /speckit.taskstoissues — tasks become GitHub issues on the board.
  6. /speckit.implement — agents execute inside their own path boundaries.
  7. /speckit.converge — measure code against spec, append the remainder, repeat.

What goes in the constitution

Written once, then every plan is checked against it. For this project the non-negotiables are:

  • Path ownership is absolute. No agent writes outside its allowlist, ever.
  • Contracts are generated. Hand-editing packages/contracts is a build failure.
  • Tokens are the only source of colour. No literal hex outside packages/tokens.
  • Web and native implement the same ui-spec entry or neither ships.
  • Auth follows RFC 9700. PKCE on every client, rotation on every refresh.
  • No public exposure, ever. Reachable on your LAN and your tailnet, never from the open internet. No Netflix branding, no content you lack rights to.
  • No third-party telemetry. Nothing reports usage anywhere. External data is fetched once at setup and committed as a fixture.
  • No hardcoded hosts. Every URL comes from env, or the TV and phone break.
07

OpenProject as the coordination substrate

Self-hosted OpenProject 17 in Docker on localhost:8080, already sitting in ../openproject-selfhost. It replaces GitHub Projects entirely: local, free, and with a far richer work-package model — types, parent/child hierarchy, relations and custom fields. OpenProject owns tickets and state. Git owns code and truth. They are never allowed to disagree.
The failure mode this section exists to prevent

Handoffs are safe when they are derived, not chosen

Free-form agent-to-agent assignment is the number one documented failure mode in multi-agent systems: A hands to B, B hands to C, C hands back to A, and each hop loses context while nobody owns the outcome. Responsibility diffusion is now the dominant failure mode in agentic systems generally, and a shared-state board has the widest blast radius of any coordination pattern — one poisoned write is inherited globally rather than passed hop by hop.

But the handoff itself is not the problem. Two properties separate a safe one from a dangerous one, and path ownership already gives you both.

 Dangerous handoffSafe handoff
Recipientchosen by the agent — “this feels like B’s problem”derived — the affected path has exactly one owner in OWNERS.yml
Done conditionsubjective. Nobody can say when it is finishedobjective and machine-checkable — the test passes
Directionany agent to any agent, so a cycle can formone-way by construction — qa-agent cannot write src, so it can never receive implementation work back
The canonical good case

qa-agent finds a bug and routes it to whoever owns the file

A test fails. The failing assertion points at a file, the file sits in a path, the path has one owner. qa-agent isn’t picking web-agent — it is performing the same lookup the router performs. This is the pattern to build, and a bug ticket is the ideal unit of agent-to-agent work precisely because its done condition is a passing test rather than an opinion.

Three guards keep it honest. 1 — Reopen, never re-file. Key the bug to the failing test id and reopen the same work package, or a fix-retest cycle silently produces twenty duplicates; then the handoff counter on that ticket is your loop detector. 2 — A bug must cite the acceptance criterion it violates. If qa-agent tested its own reading of the spec and the implementer read it differently, the “bug” is a spec ambiguity, and the implementer will dutifully break correct code to satisfy a wrong test. A ticket that cannot name a criterion is a spec question, and it routes to you. The spec has authority over correctness, not the test agent. 3 — Reproduce twice before filing, or one flaky test generates bugs forever.

Checked, and the answer is no — but it doesn’t matter

One sign-on across OpenProject and fun-world isn’t possible on the free edition

OpenProject’s OIDC provider integration is an Enterprise add-on. The documentation is explicit — “OpenID Connect providers is an Enterprise add-on” — and on Community Edition the configuration button does not even appear. SAML is Enterprise too. So pointing OpenProject at your Keycloak realm is off the table without paying.

But the thing you actually want does not need SSO. Two requirements got bundled together here, and only one of them is about identity:

  • “Agents can log tickets automatically” → solved, today, free. Agents authenticate with an API key, not an interactive login. Generate one at My account → Access tokens, then use it as a bearer token, or via basic auth with the literal username apikey and the token as password. That is all op-cli needs. SSO was never involved.
  • “One login for me” → genuinely not worth it. SSO’s value scales with users × applications. You are one person with two apps. You would be buying Enterprise to save yourself one password in a browser keychain.

If you want the single-directory experience anyway, for the learning: run LLDAP — a tiny homelab-favourite LDAP server — as the one user directory. Basic LDAP authentication is Community Edition in OpenProject (only group synchronisation is Enterprise), so OpenProject authenticates against it directly, and Keycloak federates the same directory for fun-world. One set of credentials, one place to add or remove a user. Not true single sign-on — you still log into each app — but one identity, for free.

Architecture — the part worth getting right

Build op-cli, not an MCP server

OpenProject’s official MCP server is an Enterprise add-on — Professional, Premium or Corporate only, so it is not available on the Community Edition you are running. Community MCP servers exist and work against API v3 with an API key.

Use neither. An MCP server mirrors the API, which hands every agent raw work-package access — and a mirror cannot refuse an invalid transition. Every invariant above degrades into a suggestion. A thin CLI that owns the integration can reject a hand-off that violates path ownership, enforce the fan-out cap, and increment the loop counter where an agent cannot reach it.

You already have this exact pattern in browser-test-agent: a standalone tool living outside every repo, knowing nothing about business logic, driven by an agent through Bash. Do the same again. One API key, one place to enforce the rules — and openproject-api-client is on PyPI, so it is Python, which is the point.

# every agent's first and last action — no agent ever touches the API directly
op-cli claim    --wp 42 --agent api-agent   # refuses if paths aren't owned by api-agent
op-cli split    --wp 42 --by-paths          # children derived from OWNERS.yml, never chosen
op-cli handoff  --wp 42                     # increments count; at >3 → Blocked, assigned to you
op-cli done     --wp 42 --pr 17             # links the PR, moves to In review

# specs become work packages directly — one source of truth, no GitHub Issues mirror
op-cli sync specs/008-playback/tasks.md
Where git still fits

OpenProject links pull requests via OP#123

Put OP#42 in a pull request description and OpenProject shows that PR — and the state of its GitHub Actions — on a tab of work package 42. The relationship is n:m, so one ticket can carry several PRs. That is the whole bridge: tickets and state in OpenProject, code and history in git, joined by a string in a PR body.

Note this makes Spec Kit’s /speckit.taskstoissues redundant — it targets GitHub Issues, and mirroring two ticket systems is how they drift apart. op-cli sync reads tasks.md straight into work packages instead.

On “and keep working”

Autonomy between two gates, not unbounded

Your own i18n-ticket-bot already encodes the right rule: it opens a pull request, never a direct push. Apply it here. Agents run autonomously between two human gates — you approve the spec, you approve the merge — and everything in between is theirs. An overnight loop with no gate does not produce a finished feature; it produces a large volume of plausible-looking code that all has to be read anyway.

Also throttle concurrency. Agent sprawl — too many agents with overlapping responsibilities — is a top-ranked failure mode. Ten path boundaries in OWNERS.yml is cheap and is what makes routing work; ten agents running at once is a lot of autonomous spend for one person. Define all ten, run three or four, turn it up once the loop has proven itself.

09

Auth, built in two phases so you learn it

This is the part you said you wanted to understand, so it gets built rather than installed. The target is RFC 9700 — the IETF’s current best practice, which made PKCE mandatory for every client type and refresh-token rotation standard rather than optional.
Terminology, because these get conflated

OAuth is the protocol. Passkeys are the credential. They compose.

OAuth 2.1 is authorization — delegated access to a resource. OIDC is the authentication layer on top of it that tells you who the user is. Passkeys / WebAuthn are the credential — they replace the password inside the flow, they don’t replace the flow. And Keycloak, Authentik, Pocket ID, Hanko are software that implements all of the above.

So “should I use OAuth or the popular new thing?” is a false choice: the popular new thing is passkeys, and it slots into the OAuth flow you are already building. WebAuthn is supported in every major browser as of 2026, and conditional UI — passkey autofill in the browser’s normal credential dropdown — became genuinely cross-browser once Firefox 122 shipped it. Build password + TOTP first, then add passkeys as a second credential type. Same flow, new authenticator.

Your TVs change the design — and this is a gift

You now need the Device Authorization Grant (RFC 8628)

A TV has no keyboard. Typing a password with a D-pad is miserable, and typing a passkey is impossible. This is exactly the problem RFC 8628 exists for, and it is precisely what Netflix, YouTube and Disney+ do on your TV today: the device shows a short code and a URL, you approve it on your phone, and the device polls until it is authorised.

That means fun-world’s auth server needs three grants, not one — and each is driven by a real client you actually have, which makes this a genuinely good curriculum rather than an academic exercise.

Phase 1 — you write it

Django as its own authorization server

Roughly two weeks of real learning. You implement /authorize, /token, /jwks.json and /revoke by hand; sign RS256 JWTs; store refresh tokens hashed with a family id; and get reuse detection working. Django’s user model and Argon2 hasher give you a solid base to build on rather than a black box.

By the end you will know why every one of those pieces exists — which no managed service teaches you.

Phase 2 — you replace it

Keycloak in Docker, same app code

Point the issuer at a Keycloak realm instead. Django stops issuing tokens and becomes a pure resource server validating JWTs against a remote JWKS. You get a local realm, OIDC discovery, an admin console and account management for free. Not social login — external identity providers need egress, so they are out under the zero-egress rule.

The instructive part is how little application code changes — and Keycloak is far and away the most employable IdP to have used. Budget about 1 GB of RAM in Compose.

The bit you would have paid Mux to hide

Signed playback URLs, written by you

That is essentially what Cloudflare Stream’s signed URLs do — and worth knowing that Stream offers no studio DRM either, only signed URLs and tokens. 11

Same UI, colours change — made mechanical

You asked for one UI across web and mobile with only colour varying. With two separate codebases that only holds if the build enforces it. Two mechanisms do the work: a single token source that emits both platform formats, and a ui-spec entry both implementations must satisfy.

The lint rule that makes it stick

A literal hex value anywhere outside packages/tokens fails the build, on both platforms. Without this, colour leaks into components within about a week and the guarantee is gone.

What ui-spec actually contains

Not code — a contract per component. Props, every state, dimensions in token units, focus and loading behaviour. web-agent and mobile-agent each implement it natively, and qa-agent tests both against the same entry.

Found while starting your stack — act on this

A cloudflared tunnel was in the default compose set, with a live token

docker-compose.override.yml defines a cloudflared service running tunnel --no-autoupdate run, and CF_TUNNEL_TOKEN is populated in .env. It carried no profile, so a plain docker compose up publishes this box to the public internet — and OpenProject’s first boot creates admin/admin. An internet-reachable admin panel with default credentials, on a board ten agents can write to.

Fixed: the service now sits behind a tunnel profile (override backed up alongside), so it is excluded from the default up. Exposing the box is now a deliberate act: docker compose --profile tunnel up -d. Still yours to do: change the admin password on first login, and revoke that tunnel token if the Cloudflare hostname it points at is no longer one you control.
